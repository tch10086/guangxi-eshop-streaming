# 项目总结与技术复盘

## 一、做成了什么

一套可以在单台虚拟机上跑通的流批一体数据分析系统：

- 采集：Kafka 生产者模拟 8 类广西农产品订单，支持异常单、重复单号、迟到数据三类注入
- 实时：Structured Streaming 消费订单流，60 秒水印 + HDFS Checkpoint + ForeachBatch 写 MySQL
- 离线：Hive ODS-DWD-DWS-ADS 四层数仓，SparkSQL ETL，含清洗、去重、多维聚合、客单价计算
- 应用：Flask 四个接口 + ECharts 大屏（4 卡 4 图 + 告警列表 + 预测曲线）
- 拓展：线性回归品类销量预测 + KMeans 品类画像聚类
- 工程：一键安装脚本、一键启停脚本、故障排查手册、12 条测试用例

## 二、几个关键技术决定

**1. 流批共用一个 process_batch()**
不是为了"看起来高级"，而是解决真实痛点：如果实时和离线各写一套聚合逻辑，同一个"成交额"迟早会出现两个值。
现在批模式只换输入源，口径天然一致，也让"重跑历史"变成一行命令。

**2. 去重键不用 order_id，而是构造 dedup_key**
`dropDuplicates` 把 NULL 视为相等，订单号缺失的行会被合并成一条，异常单统计直接少一大截。
改成"正常用订单号、缺失用 Kafka 时间戳"后，既去重又不漏异常。

**3. 异常订单单独建表，不进 ADS 成交口径**
脏数据的金额本身不可信，混进成交额会让经营指标失真。异常进 `dwd_eshop_order_abnormal` 并驱动大屏告警，
有效口径只统计通过校验的订单。

**4. 实时表用累加式 UPSERT，而不是覆盖**
覆盖写会把历史累计冲掉。改成 `ON DUPLICATE KEY UPDATE` 累加后，还要注意 MySQL 是从左到右赋值的——
`avg_price` 必须写在 `order_cnt` 之前，否则分母变成加上本批之后的值，客单价会被稀释。

**5. 大屏优先查实时表，DWS 兜底**
原资源包没有 MySQL 建表脚本，接口却要查 dws 表，直接跑必然 500。
补齐建表后仍然加了兜底逻辑：即使离线 ETL 还没跑，实时板块也能先出图，不会整页空白。

## 三、遇到的问题与解决（技术复盘）

| 现象 | 定位过程 | 解决 |
| --- | --- | --- |
| Flask 一访问就 500 | 日志是 `Object of type Decimal is not JSON serializable`；对比同文件里 dayTrend 用了 float() 却没报错，锁定实时那段 | 抽出 `to_jsonable()` 统一转换 Decimal/datetime |
| Spark 报找不到 kafka 数据源 | 预编译包只带基础依赖 | 把 4 个连接器 jar 放进 `$SPARK_HOME/jars` |
| 品类图、地市图全空 | 接口查 MySQL 的 dws 表，但资源包只给了 Hive 建表 | 补 `mysql_ddl.sql`，接口加兜底 |
| Hive 启动报 guava 方法找不到 | Hive 3.1.2 自带 guava-19，Hadoop 3.3 用 guava-27 | 用 Hadoop 的 guava 替换 Hive 的 |
| CentOS7 `yum` 全部失效 | 7 已 EOL，官方镜像下线 | 换阿里云 vault 源，或挂 ISO 做本地源 |
| Kafka 重启报 `node already exists` | 非正常关机后 ZK 里残留旧会话的 `/brokers/ids/0` | 杀残留进程重启，必要时手动删节点 |
| 安装时卡在 "Starting automated install" | 重建 ISO 时用了 Windows 挂载，长文件名被截断，repodata 里的 primary.xml.gz 名字对不上 | 用 bsdtar 按 Rock Ridge 解包，重建时加 `-joliet-long` |
| 宿主机 SSH 频繁超时 | 虚拟机给 8G 后宿主机只剩 1G 可用，全机卡顿 | 降到 6G，栈内 JVM 参数保持默认 |

这些问题有一个共同点：**报错信息往往指向症状，不指向原因**。
比如 Decimal 那个问题，真正的原因不是"Flask 不支持 Decimal"，而是"某处忘了做类型转换"；
ISO 那个问题，真正的错在打包工具，不在 anaconda。

## 四、不足

1. **数据规模小**：单机伪分布式、单分区 Topic、local[2]，体现不出并行度和背压。
2. **写入方式朴素**：每个微批逐条 UPSERT，没有批量合并与连接池，吞吐上限低。
3. **异常识别只有规则**：没有基线检测，识别不了"同一买家短时间高频下单"这类刷单行为。
4. **没有告警通道**：只能盯着大屏看，运营不看屏幕就收不到提醒。
5. **预测模型偏简单**：线性回归搞不定促销、节假日的突变，MAE 只能当参考。
6. **至少一次语义**：写 MySQL 是累加式 UPSERT，任务重跑会重复累加，靠批模式前先 TRUNCATE 规避，不是严格幂等。

## 五、下一步可以怎么做

- 写入改造：JDBC batch 或先落 Hive 再统一同步，配连接池
- 并行改造：Kafka 多分区 + 提高并行度 + `maxOffsetsPerTrigger` 背压调优
- 异常升级：规则 + 近 7 天同时段均值 ± 3σ 的统计基线，加频次风控
- 告警通道：异常订单推到企业微信或邮件
- 预测升级：换 Prophet 或 LightGBM，加入节假日、促销特征，做滚动回测
- 工程化：把参数抽成配置文件，加单元测试，接入调度（DolphinScheduler / Airflow）

## 六、一句总结

这套系统最大的价值不是"用了多少组件"，而是把一条链路从数据产生到界面展示完整走通，
并且知道每一跳失败时该去哪儿看。这比单独会写一个 Spark 作业要难，也更有用。
